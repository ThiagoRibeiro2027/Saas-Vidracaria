**ADR-003 — Cliente-Piloto**

**Status:** APROVADO\
**Versão:** 2.1\
**Tipo:** Architecture Decision Record (ADR)\
**Data:** 2026-09-09\
**Decisão:** Definição, governança e critérios do cliente-piloto\
**Cliente-piloto:** JR Box\
**Responsável interno:** Rafael\
**Período previsto:** 01/10/2026 a 15/10/2026\
**Duração prevista:** 15 dias corridos\
**Decisões vinculadas:** ADR-001, ADR-002, ADR-004, ADR-005, ADR-007 e
ADR-008

**1. Contexto**

O SaaS será validado inicialmente por meio de uma operação-piloto em uma
empresa real do segmento de vidraçaria.

O piloto tem como finalidade validar o produto em condições reais de
operação, utilizando usuários, dados, pedidos, processos e exceções
reais.

O piloto não deverá ser tratado como desenvolvimento de um sistema
exclusivo para o cliente.

A empresa-piloto será utilizada como ambiente de validação das hipóteses
do produto e da capacidade do SaaS de suportar o fluxo operacional
definido no ADR-002.

**2. Cliente-piloto definido**

O cliente-piloto definido para esta etapa é:

**JR Box**

O cliente-piloto será utilizado como referência prática para validar:

fluxo operacional;

usabilidade;

regras de negócio;

consistência dos dados;

permissões;

rastreabilidade;

desempenho operacional;

tratamento de exceções;

funcionamento offline quando aplicável;

notificações;

requisitos fiscais efetivamente necessários;

demais hipóteses relevantes do MVP.

A utilização da JR Box não altera o caráter genérico do produto.

**3. Responsável interno**

O responsável interno pelo acompanhamento do piloto será:

**Rafael**

O responsável deverá atuar como ponto central de acompanhamento da
operação-piloto e deverá:

coordenar a utilização do sistema;

acompanhar problemas e dúvidas;

registrar feedbacks;

acompanhar incidentes;

auxiliar na classificação das necessidades identificadas;

acompanhar critérios de sucesso;

consolidar informações para avaliação do piloto;

apoiar a decisão de encerramento ou continuidade.

A responsabilidade não significa que Rafael será o único usuário ou
responsável pela execução das atividades operacionais.

**4. Período do piloto**

O período previsto para o piloto será:

**Início:** 01/10/2026\
**Término previsto:** 15/10/2026\
**Duração:** 15 dias corridos

O período será utilizado para avaliação inicial do produto em operação
real.

A duração poderá ser alterada caso evidências do uso real demonstrem
necessidade de:

extensão;

interrupção antecipada;

repetição de determinada etapa;

correção de problemas críticos;

ampliação controlada da validação.

Qualquer alteração relevante deverá ser registrada e justificada.

**5. Objetivo do piloto**

O objetivo principal é verificar se o MVP consegue sustentar uma
operação real de ponta a ponta.

O piloto deverá validar, principalmente:

execução do fluxo operacional;

continuidade das informações entre etapas;

execução das responsabilidades pelos usuários;

tratamento das principais exceções;

integridade dos dados;

segurança;

isolamento entre empresas;

rastreabilidade;

usabilidade;

capacidade de utilização com dados reais.

O objetivo não é validar a totalidade do produto futuro.

**6. Fluxo a ser validado**

Sempre que aplicável à operação da JR Box, deverá ser validado o fluxo:

**Orçamento → Aprovação/Conversão → Conferência → Liberação → Engenharia
→ Reserva/Disponibilidade → Produção → Controle necessário → Expedição →
Instalação → Aceite/Conclusão → Encerramento.**

O piloto deverá observar também os cenários excepcionais relevantes.

**7. Dados reais**

A validação deverá utilizar dados reais do cliente-piloto.

Poderão ser utilizados:

clientes reais;

produtos reais;

materiais reais;

componentes reais;

fornecedores quando necessários;

preços reais;

pedidos reais;

medidas reais;

informações técnicas reais;

usuários reais;

obras reais, quando aplicável.

Os dados deverão ser tratados conforme as regras de segurança, acesso,
privacidade e LGPD aplicáveis.

O uso de dados fictícios isoladamente não será suficiente para validar o
piloto.

**8. Preparação inicial dos dados**

A preparação dos dados poderá utilizar a funcionalidade de importação
inicial controlada definida no ADR-002.

Quando necessário, poderão ser utilizados arquivos estruturados para
carregar:

clientes;

produtos;

materiais;

componentes;

fornecedores;

preços;

demais dados necessários.

A importação deverá possuir:

validação;

identificação de erros;

conferência;

controle de duplicidades;

auditoria.

Não é objetivo do piloto realizar uma migração histórica completa.

**9. Usuários e treinamento**

Os usuários participantes deverão possuir acesso compatível com suas
responsabilidades.

O acesso deverá respeitar o ADR-001.

Antes da utilização operacional, deverá existir preparação mínima dos
usuários, contemplando:

acesso ao sistema;

responsabilidades;

fluxo de trabalho;

principais funcionalidades;

tratamento de erros;

procedimentos para situações excepcionais;

utilização offline quando aplicável.

O treinamento deverá ser suficiente para permitir a utilização real sem
transformar o piloto em um programa extensivo de capacitação.

**10. Governança do piloto**

O piloto deverá possuir acompanhamento estruturado.

Problemas, sugestões e solicitações deverão ser registrados.

Cada ocorrência deverá ser classificada, sempre que possível, como:

defeito;

erro de dados;

erro de configuração;

necessidade essencial do produto;

melhoria;

necessidade específica do cliente;

dúvida operacional;

solicitação fora do escopo.

A classificação deverá evitar que toda solicitação seja automaticamente
tratada como requisito de desenvolvimento.

**11. Feedback**

O feedback deverá ser coletado de forma estruturada.

Para cada feedback relevante, registrar:

origem;

usuário;

contexto;

processo afetado;

descrição;

impacto;

frequência;

criticidade;

classificação;

decisão;

responsável;

status.

Feedbacks deverão ser analisados considerando o produto como um todo, e
não somente a necessidade imediata do cliente-piloto.

**12. Critérios para alteração do MVP**

Uma necessidade identificada durante o piloto poderá justificar
alteração do MVP quando:

bloquear o fluxo principal;

comprometer integridade dos dados;

comprometer segurança;

representar obrigação legal;

demonstrar erro em uma premissa fundamental do produto;

for indispensável ao propósito do produto.

Solicitações específicas da JR Box não deverão entrar automaticamente no
produto.

Deverá ser avaliado se a necessidade representa:

configuração;

funcionalidade padrão;

melhoria futura;

customização controlada;

solicitação não aplicável ao produto.

Alterações relevantes deverão seguir a governança definida no ADR-002.

**13. Segurança e dados**

Durante todo o piloto deverão ser preservados:

isolamento entre empresas;

controle de acesso;

autorização no backend;

rastreabilidade;

auditoria;

integridade dos dados;

proteção das informações;

privacidade;

segurança das credenciais;

controle de acesso aos dados do cliente-piloto.

Falhas graves de segurança ou isolamento deverão ser tratadas como
prioridade máxima.

**14. Operação offline**

Quando houver utilização offline, deverão ser observadas as regras dos
ADR-005 e ADR-008.

O piloto deverá validar, quando aplicável:

armazenamento local;

fila de operações;

sincronização;

idempotência;

revalidação no servidor;

tratamento de conflitos;

recuperação de erros;

confirmação do servidor.

O funcionamento offline não deverá transformar os dados locais em fonte
oficial do sistema.

**15. Notificações**

As notificações deverão ser avaliadas conforme os ADR-007 e ADR-008.

O piloto deverá observar:

notificações internas;

e-mail;

push quando aplicável;

comportamento em situações de falha;

preferências;

criticidade;

rastreabilidade.

Falhas em canais externos de comunicação não deverão impedir o fluxo
operacional principal.

**16. Fiscal**

As necessidades fiscais identificadas durante o piloto deverão ser
analisadas conforme o ADR-004.

O piloto deverá evitar desenvolvimento fiscal baseado em hipóteses.

Somente cenários efetivamente necessários à operação real deverão ser
considerados para o MVP.

**17. Indicadores do piloto**

O piloto deverá acompanhar, sempre que possível:

quantidade de pedidos processados;

quantidade de usuários ativos;

etapas utilizadas;

pedidos concluídos;

pedidos parciais;

ocorrências;

bloqueios;

retrabalhos;

erros;

tempo de execução;

falhas de sincronização;

problemas de dados;

solicitações de melhoria;

dependência de processos externos.

Os indicadores devem servir para avaliar a operação, e não criar uma
estrutura de BI avançado dentro do MVP.

**18. Critérios de sucesso**

O piloto será considerado bem-sucedido quando demonstrar, em conjunto,
que:

pedidos reais podem ser processados;

o fluxo principal pode ser executado de ponta a ponta;

os usuários conseguem executar suas responsabilidades;

os dados permanecem consistentes;

existe rastreabilidade;

os principais bloqueios podem ser tratados;

operações parciais são representadas corretamente;

o isolamento entre empresas é preservado;

o sistema reduz a dependência de controles externos para o núcleo da
operação;

os principais problemas podem ser identificados e classificados;

o produto demonstra potencial de utilização contínua após o piloto.

O sucesso não exige que todas as funcionalidades do produto futuro
estejam implementadas.

**19. Critérios de falha ou interrupção**

O piloto poderá ser interrompido ou ter seu escopo temporariamente
reduzido quando houver:

falha grave de segurança;

vazamento entre empresas;

perda significativa de dados;

inconsistência crítica;

impossibilidade de executar o fluxo principal;

falha estrutural que impeça a utilização;

descumprimento legal relevante;

impossibilidade operacional de continuidade.

A interrupção deverá ser registrada e analisada antes de eventual
retomada.

**20. Avaliação final**

Ao final do período previsto, deverá ser realizada avaliação formal do
piloto.

A avaliação deverá considerar:

resultados obtidos;

objetivos atingidos;

problemas encontrados;

feedback dos usuários;

indicadores;

estabilidade;

segurança;

integridade;

rastreabilidade;

aderência ao fluxo;

necessidades identificadas;

alterações realizadas durante o piloto;

backlog gerado.

**21. Resultado do piloto**

Ao final da avaliação, o piloto deverá resultar em uma das seguintes
classificações:

**A — Aprovado**

O MVP demonstrou capacidade suficiente para utilização e evolução.

**B — Aprovado com ajustes**

O produto demonstrou viabilidade, mas necessita de correções ou
melhorias relevantes antes da expansão.

**C — Requer nova validação**

O produto possui potencial, mas as evidências obtidas ainda não são
suficientes para conclusão.

**D — Reavaliar premissa**

As evidências demonstraram que uma ou mais premissas fundamentais do
produto precisam ser revistas.

A classificação deverá ser documentada.

**22. Continuidade após o piloto**

O encerramento do piloto não significa necessariamente encerramento do
produto.

Dependendo do resultado, poderá ocorrer:

continuidade da operação;

correções;

nova rodada de validação;

expansão controlada;

priorização da Release 1;

revisão de determinadas decisões;

reavaliação de premissas.

Qualquer alteração estrutural deverá ser registrada no documento
apropriado.

**23. Governança de mudanças**

Durante o piloto, nenhuma solicitação deverá alterar silenciosamente:

arquitetura;

escopo do MVP;

regras de segurança;

modelo de permissões;

modelo de dados;

decisões dos ADRs.

Alterações relevantes deverão ser registradas formalmente.

O piloto é instrumento de validação, não mecanismo de alteração informal
da arquitetura.

**25. Riscos**

Os principais riscos do piloto são:

utilização insuficiente do sistema;

dados inadequados;

treinamento insuficiente;

resistência operacional;

problemas de integração;

falhas de sincronização;

descoberta de requisitos não previstos;

excesso de solicitações específicas;

tentativa de ampliar o MVP;

problemas de segurança;

inconsistência entre processos reais e modelo do sistema.

Esses riscos deverão ser monitorados durante todo o período.

**26. Princípio central**

O cliente-piloto deve ser utilizado para responder à seguinte pergunta:

**O produto definido no MVP consegue resolver, de forma confiável, o
problema operacional para o qual foi criado?**

O objetivo não é perguntar:

<span dir="rtl">“</span>O que a JR Box gostaria que fosse desenvolvido?”

A diferença é fundamental para impedir que o piloto se transforme em
projeto sob medida.

**27. Consequências aceitas**

A decisão aceita:

utilização de dados reais;

ajustes decorrentes de evidências;

correções durante o piloto;

algumas atividades ainda realizadas externamente;

evolução posterior do produto;

possibilidade de nova rodada de validação;

existência de funcionalidades ainda incompletas.

Não são aceitos:

perda de dados;

comprometimento de segurança;

vazamento entre empresas;

ausência de rastreabilidade essencial;

alterações informais de arquitetura;

transformação do MVP em sistema exclusivo para a JR Box.

**28. Resultado esperado**

Ao final do piloto, deverá existir evidência suficiente para determinar
se o MVP:

funciona em uma operação real;

suporta o fluxo operacional principal;

preserva dados e rastreabilidade;

atende às responsabilidades dos usuários;

trata as principais exceções;

possui segurança e isolamento adequados;

apresenta condições de evolução para a próxima etapa.

O piloto deverá produzir aprendizado suficiente para orientar a evolução
do produto sem comprometer sua natureza de SaaS genérico.
